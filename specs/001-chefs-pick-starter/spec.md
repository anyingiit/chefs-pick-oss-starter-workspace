# Feature Specification: 主厨精选开源仓库起步模板（Chef's Pick OSS Starter）

**Feature Branch**: `001-chefs-pick-starter`（当前目录尚未初始化 Git，未创建对应分支）

**Created**: 2026-09-17

**Status**: Draft

**Input**: User description: "根据最后一篇文档（调研报告修订版）创建一个开源仓库，帮助个人项目和团队项目快速起步。市面上没有现成的'主厨精选'仓库，但各模块的佼佼者已基本有明确答案；本仓库免去使用者搜集和拼接的麻烦，开箱即用地提供完整仓库的全部核心要素。亮点是每个模块的选择都有社区依据，并标注来源和大致使用人数（估算）或 Star 数；多个选项同样合格时，可按作者喜好选择。选择顺序：先看社区认可度，认可度相当时，看是否易于仓库持有者起步。"完整输入（交接文档、两份调研报告和请求原文）逐字保存在 [input.md](./input.md)。

## Clarifications

### Session 2026-09-17

- Q: 个人版和团队版如何组织？ → A: 只做个人版。可以附一份升级为团队项目的简要指引，但属于次要内容；如果难以做好，可以不做。
- Q: 模板仓库自身用什么许可证？ → A: MIT。说明文档另行声明：从本模板生成的项目无需保留模板作者署名。
- Q: 文档用什么语言？ → A: 模板自身的说明文档（含选型清单）用中英双语；生成仓库中的协作文件用英文。
- Q: 模板要不要内置各编程语言的项目脚手架，还是只提供与语言无关的文件？ → A: 只做与语言无关的文件；选型清单也不推荐任何语言的脚手架，选型清单本身保留。
- Q: 每个模块的来源和认可度数据应该展示在哪里，又该多久复核一次？ → A: 三处展示：独立的选型清单文件（完整数据）、模板首页摘要表、生成仓库各文件内的一行来源注释（渲染时不可见）。数据至少每 6 个月复核一次，每次发布前也要复核。
- Q: 模板仓库的标题、简介（About）和主题标签（Topics），是否采用交接文档第 4 节的建议？ → A: 全部照原建议采用，简介只用英文。
- Q: 生成仓库的自动检查和依赖更新配置引用 GitHub 动作（actions）时，应该怎样固定版本？ → A: 所有动作都固定到完整的提交哈希，行尾注明版本号，由依赖自动更新定期升级；工作流令牌默认只读。
- Q: 发布前要用什么方式验证 SC-009、SC-011 这类"别人实际用起来顺不顺手"的指标？ → A: 作者会在发布后马上自己使用；这类指标不作为发布门槛。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 个人开发者一键获得"五脏俱全"的新仓库 (Priority: P1)

独立开发者有了新想法，想马上开一个开源仓库。从本模板创建新仓库后，开发者立即拥有完整开源仓库的全部核心要素：项目说明、许可证、忽略规则、行为准则、贡献指南、安全策略、Issue 表单、合并请求模板、变更日志、发布说明分类、自动检查（持续集成）和依赖自动更新。开发者只需按一份简短的起步清单替换项目名、作者、联系方式等身份信息，就能回到自己的创作上，不必再逐个搜集、比较和拼接这些文件。

**Why this priority**: 这是项目存在的根本理由：开箱即用，免去拼接。只交付这一条，就已经是一个可用的起步模板（MVP）。

**Independent Test**: 从模板创建一个全新仓库，按起步清单完成定制，然后检查四点：核心模块齐全；没有遗留占位符；GitHub 社区标准自检页全部达标；首次自动检查通过。

**Acceptance Scenarios**:

1. **Given** 使用者从未配置过任何社区健康文件，**When** 从本模板创建新仓库，**Then** 新仓库无需额外下载或复制，即包含核心清单（FR-003）中的全部必需与推荐模块。
2. **Given** 刚生成的新仓库，**When** 使用者按起步清单完成全部必做步骤，**Then** GitHub 社区标准自检页（Insights → Community Standards）上的全部检查项均显示为已完成。
3. **Given** 使用者尚未完成定制，**When** 在仓库内搜索统一的占位符标记，**Then** 一次搜索即可找出全部待替换的身份信息，且不存在起步清单之外的隐藏占位符。
4. **Given** 刚生成、尚未添加任何代码的新仓库，**When** 首次推送或发起合并请求，**Then** 自动检查成功完成，不会因为仓库里还没有代码而失败。
5. **Given** 刚生成的新仓库，**When** 使用者浏览仓库中的文件，**Then** 作为项目自身信息出现的内容中，找不到模板作者的身份信息（如项目许可证中的版权署名、赞助链接、联系邮箱），项目的变更日志里也没有模板自身的版本历史；模板自身的介绍、讲解、许可证声明等内容，只出现在明确标注的起步引导层中。

### User Story 2 - 潜在使用者核查每个模块的选型依据，从而信任这个模板 (Priority: P1)

决定是否采用本模板之前，访问者想知道：每个模块选的是谁，为什么选它，社区认可度有多高。访问者从模板首页出发，能看到一份完整的"主厨精选"清单，内容包括每个模块的选定来源（附链接）、认可度证据（Star 数、估算使用人数、官方地位，或事实标准及其采用者举例）、数据核实日期、入选理由和考虑过的备选方案。据此，访问者能判断这些选择是社区公认的佼佼者，而不是作者的一厢情愿。

**Why this priority**: 这是本项目区别于其他模板的核心亮点。没有可核查的依据，本模板就只是"又一个模板"。它和用户故事 1 都必须在首个版本中交付。单独交付时，它本身也是一份有价值的"各模块佼佼者"参考清单。

**Independent Test**: 只打开模板仓库首页，不生成新仓库。逐一核对交付的每个模块，确认从首页出发一次点击内就能找到它的来源、认可度证据、核实日期和入选理由。

**Acceptance Scenarios**:

1. **Given** 访问者位于模板仓库首页，**When** 寻找选型依据，**Then** 一次点击内即可到达覆盖全部模块的选型清单。
2. **Given** 选型清单中的任一模块，**When** 访问者阅读该条目，**Then** 能看到选定来源及链接、认可度证据、核实日期、入选理由和级别（必需、推荐或可选）。
3. **Given** 某模块有多个同样合格的候选，**When** 访问者阅读该条目，**Then** 条目列出备选方案，并说明最终取舍依据的是"起步更容易"还是作者个人偏好。
4. **Given** 某模块的认可度无法用 Star 数表示（如平台官方功能、没有单一代码仓库的规范），**When** 访问者阅读该条目，**Then** 条目给出其他类型的证据（如"GitHub 官方功能"或"事实标准，采用者包括……"），而不是留空或编造数字。
5. **Given** 某个知名度很高的候选被刻意排除（如 golang-standards/project-layout），**When** 访问者阅读清单，**Then** 能看到排除理由，从而理解"只看 Star 数不够"这一选型原则。

### User Story 3 - 生成仓库的外部贡献者获得清晰的参与路径 (Priority: P2)

有人在用本模板生成的仓库里想报告缺陷、提出功能建议、提交代码，或者私下报告安全漏洞。进入仓库后，这位贡献者能通过结构化表单提交信息完整的 Issue，发起合并请求时自动看到自检清单，还能找到行为准则、贡献流程和私下报告漏洞的渠道。

**Why this priority**: "五脏俱全"给仓库持有者的实际回报就在这里：减少来回追问，减少低质量 Issue，避免漏洞被公开暴露。这个故事建立在用户故事 1 的文件之上，验收的是这些文件的内容质量。

**Independent Test**: 在一个已按起步清单完成定制的生成仓库中，以外部贡献者身份分别新建 Issue、发起合并请求、查找漏洞报告入口，检查每一步的引导是否完整。

**Acceptance Scenarios**:

1. **Given** 外部贡献者点击新建 Issue，**When** 选择 Issue 类型，**Then** 能看到"缺陷报告"和"功能建议"两个结构化表单，以及把使用求助引到其他渠道（如讨论区）的链接；空白 Issue 默认关闭。
2. **Given** 外部贡献者在填写缺陷报告表单，**When** 必填项（复现步骤、期望行为与实际行为、运行环境）没有填写，**Then** 表单无法提交，并提示需要补充哪些信息。
3. **Given** 外部贡献者发起合并请求，**When** 打开编辑界面，**Then** 描述框已预先填好变更说明、关联 Issue 和自检清单。
4. **Given** 安全研究者发现了漏洞，**When** 查看安全策略，**Then** 能看到受支持的版本范围和私下报告的方式，并被明确告知不要公开提交 Issue。
5. **Given** 仓库持有者要发布新版本，**When** 使用平台自动生成发布说明，**Then** 变更按"新功能 / 修复 / 其他"分类归组。

### User Story 4 - 模板维护者复核认可度数据并更新选型 (Priority: P3)

Star 数和维护状态会随时间变化。模板维护者需要定期复核每个模块的数据：更新数字和核实日期；发现上游停滞、被取代，或出现认可度更高的新候选时，按既定选型规则重新评估，并把变化记录下来告知使用者。

**Why this priority**: 它保证信任依据长期有效。首个版本发布时数据刚核实完，所以可以晚于前两个故事实施。

**Independent Test**: 按维护说明完整执行一次复核：更新数据和核实日期；再模拟一个"上游 12 个月没有提交"的情况，走一遍重新评估流程，确认结论和变更记录都可以追溯。

**Acceptance Scenarios**:

1. **Given** 距上次核实已满 6 个月，或准备发布新版本，**When** 维护者按维护说明复核，**Then** 每条认可度数据都被更新或确认，并带上新的核实日期。
2. **Given** 某上游来源末次提交超过 12 个月，或依赖了已被广泛弃用的工具，**When** 维护者复核，**Then** 该模块被标记为"需重新评估"，并按选型规则得出保留或替换的结论。
3. **Given** 选型发生了变化，**When** 模板发布新版本，**Then** 模板自身的变更记录写明替换了什么、为什么替换，已生成仓库的持有者可据此自行决定是否跟进。

### User Story 5 - 项目发展为多人协作后，持有者获得简要的升级指引 (Priority: P4，可选)

个人项目有了固定的协作者，逐渐变成多人维护。仓库持有者想知道：团队项目通常还要补充哪些能力，每项该选谁。模板可以附一份简要指引，列出团队常用的增强项（如代码负责人的团队用法、提交前检查、团队适用的依赖更新方案、仓库健康度评分），附上它们的来源和认可度，并说明什么时候需要基金会级治理。

**Why this priority**: 本期只做个人版。这份指引是次要的附加内容，如果难以做到简洁可靠，可以不提供，不影响本期验收。

**Independent Test**: 在模板仓库中找到升级指引，确认每个增强项都附有来源和认可度，并且整份指引能在 5 分钟内读完。

**Acceptance Scenarios**:

1. **Given** 个人项目开始多人协作，**When** 持有者阅读升级指引，**Then** 能看到团队常用增强项的清单，以及每项的作用、来源和认可度。
2. **Given** 项目需要基金会级的治理结构，**When** 持有者阅读升级指引，**Then** 能找到治理类模板和开源最佳实践徽章的推荐，并了解什么情况下需要升级到这一级别。
3. **Given** 本期最终决定不提供升级指引，**When** 验收本期交付，**Then** 其余用户故事的验收不受影响。

### Edge Cases

- **账号级默认 Issue 模板被整体覆盖**：生成的仓库自带 Issue 表单目录。只要这个目录里有任何文件，使用者账号级 `.github` 仓库中的默认 Issue 模板就会全部失效。说明文档必须提示这一点，并告诉想沿用账号默认模板的使用者该怎么做。
- **许可证无法由账号统一下发**：许可证不能作为账号级默认社区健康文件，因此每个生成仓库都必须自带许可证文件。
- **私有漏洞报告未开启**：安全策略引导报告者使用私有漏洞报告按钮，但如果仓库持有者没有在设置中开启该功能，按钮就不会出现。起步清单必须把"开启私有漏洞报告"列为必做步骤，安全策略中也要给出备用联系方式。
- **讨论区未开启**：Issue 入口把使用求助引到讨论区，但新仓库默认不开启讨论区，链接会失效。起步清单必须提示开启讨论区，或把链接改到其他求助渠道。
- **占位符未替换**：项目名、所有者、联系邮箱等占位符没有替换时，链接和举报渠道都会失效。所有占位符必须使用统一、可搜索的标记，并在起步清单中逐一列出。
- **模板与生成项目的"双重身份"**：模板仓库自己也需要项目说明、许可证、变更日志等文件，但 GitHub 会把默认分支上的文件原样复制到每个生成仓库。模板作者的身份信息和赞助链接不得作为生成项目自身的信息出现，模板自身的版本历史也不得出现在项目的变更日志里；模板自身的介绍、讲解、选型清单、维护说明、许可证声明和变更记录，只能放在可一步移除的起步引导层中。生成仓库应得到干净的项目骨架（例如只有"未发布"一节的变更日志）。
- **生成的仓库里还没有代码**：语言无关的自动检查在空仓库上也必须成功，并清楚标出使用者接入自己语言的检查和测试的位置。
- **依赖自动更新暂时没有可管理的依赖**：新仓库还没有语言依赖清单时，依赖更新只管理自动检查所用的动作（actions）版本，这项更新本身仍然有效；使用者添加语言依赖时，有说明可以照着做。
- **分类标签被删除或改名**：Issue 表单和发布说明分类依赖 GitHub 新仓库自带的默认标签（如 bug、enhancement）。使用者删除或改名这些标签后，相关变更会被归入"其他"，而不会报错；说明文档应列出这些依赖的标签。
- **使用者不需要某个推荐或可选模块**：删除任一推荐或可选模块后，其余模块必须照常工作（例如删除变更日志不会导致自动检查失败）。说明文档要列出每个模块的删除方法和删除后的影响。
- **可选模块的副作用**：可选模块在默认状态下不得产生可见的副作用，例如不得出现指向不存在账户的赞助按钮，也不得自动请求不存在的审阅者。
- **上游许可证与署名**：收录或改写的上游内容各有许可证，例如行为准则采用知识共享署名许可，要求保留署名。必须保留上游要求的署名，同时不能给生成仓库的持有者增加额外的合规负担。
- **认可度数据缺失或无法精确获取**：有些规范没有能代表整体采用量的单一代码仓库（如 Contributor Covenant），有些数据可能暂时取不到。这类条目必须标注"未取得"或给出替代证据，不得编造。
- **Star 数高但不权威**：只凭 Star 数入选的候选（如非官方、却以"标准"自居的目录布局项目）必须被排除，并在清单中作为反例说明。
- **行为准则存在多个通行版本**：最新正式版是 3.0（2025 年发布，改用 CC BY-SA 4.0 许可）；2.1 是 2.x 系列的最新版；GitHub 的行为准则接口目前提供的仍是 2.0。清单必须说明选了哪个版本、为什么选它，并提及其他版本。
- **数据过时**：核实日期超过复核周期后，使用者应能从清单上看出数据可能已经过时。
- **使用者新增的动作没有固定哈希**：使用者按项目语言接入检查时，可能直接用版本标签引用新动作。依赖自动更新只会升级已有的引用，不会把版本标签改成哈希，所以说明文档必须给出固定哈希的做法。
- **不适合加注释的文件**：在许可证文件中加入来源注释，可能影响 GitHub 识别许可证类型。这类文件不加注释，改由选型清单追溯来源。
- **已生成的仓库不会随模板更新**：GitHub 从模板生成的仓库与模板之间没有同步关系。模板的后续改进只能通过模板变更记录告知使用者，由使用者自行决定是否跟进。

## Requirements *(mandatory)*

### Functional Requirements

**交付方式与范围**

- **FR-001**: 使用者必须能通过 GitHub"从模板创建仓库"功能一步生成新仓库，无需安装任何额外工具，也无需运行脚手架生成器。
- **FR-002**: 模板只交付面向个人项目的核心方案，不提供团队版。团队级增强只出现在可选的升级指引中（见 FR-004）。
- **FR-003**: 核心方案必须包含以下"五脏俱全"模块，并标注级别：
  - 必需：项目说明（README）、许可证、忽略规则。
  - 推荐：行为准则、贡献指南、安全策略、Issue 表单（缺陷报告、功能建议、Issue 入口配置）、合并请求模板、变更日志、发布说明分类配置、自动检查（持续集成）、依赖自动更新。
  - 可选：编辑器统一格式配置、提交前检查、代码负责人、赞助入口、变更日志自动化（只推荐，默认不启用）。
- **FR-004**: 模板可以附带一份简要的"升级为团队项目"指引，列出团队常用的增强项（如代码负责人的团队用法、提交前检查、团队适用的依赖更新方案、仓库健康度评分与仓库规则检查），附上来源和认可度，并说明什么情况下需要基金会级治理（治理类模板、开源最佳实践徽章）。这份指引是次要内容：如果难以做到简洁可靠，可以不提供，本期验收不以它为前提。
- **FR-005**: 模板只提供与编程语言无关的文件，不内置任何语言相关的项目脚手架，选型清单也不推荐语言脚手架。与语言相关的内容仅限于指引使用者自行补充（忽略规则、自动检查、依赖更新，见 FR-009、FR-015、FR-022、FR-023）。
- **FR-006**: 重型脚手架和基金会级成套模板不得作为默认方案，也不纳入本模板。选型清单可以把它们列为"不适合个人项目"的参考，并说明原因。

**开箱即用与定制**

- **FR-007**: 生成仓库中的文件必须是已经填好、可以直接使用的内容，而不是只有"TODO"的空壳。只有项目专属信息使用占位符，即只有仓库持有者才能提供的内容，如项目名、简介、所有者、版权人、联系方式、年份、使用示例。
- **FR-008**: 所有占位符必须使用统一的标记格式，一次搜索就能全部找到。
- **FR-009**: 模板必须提供一份起步清单，按顺序列出生成仓库后需要完成的全部步骤，并区分必做与选做。清单至少包括：替换全部占位符；填写仓库简介等社区标准自检页会检查的仓库设置；开启私有漏洞报告；开启讨论区，或修改求助链接；确认许可证类型和版权人；按项目语言补充忽略规则、自动检查和依赖更新；决定每个推荐和可选模块是否保留；用社区标准自检页验收。
- **FR-010**: 本规格中的"生效"指某项内容作为生成项目自身的信息出现，例如出现在项目的许可证版权人、赞助入口、安全策略或行为准则的联系方式、项目变更日志中；起步引导层（FR-012）中的内容不属于生效，它们标注为模板内容，并在起步完成后随引导层一并移除。模板作者本人的身份信息（作者署名、联系方式、赞助链接）不得作为生成项目自身的信息出现，例如出现在项目许可证的版权人、赞助入口、安全策略或行为准则的联系方式中；模板自身的版本历史也不得作为生成项目的变更记录出现。生成仓库中的对应位置必须是占位符或干净的初始骨架。模板自身的介绍、讲解、选型清单、维护说明、许可证声明和变更记录，按 FR-011、FR-012 放在起步引导层中。
- **FR-011**: 生成仓库的项目说明（README）必须基于选定的 README 模板，提供项目骨架（项目名与简介、安装、使用、许可证等章节），并且从生成那一刻起就位于项目说明的正式位置。模板自身的介绍属于起步引导层，在生成仓库中最多一步即可移除。
- **FR-012**: 模板必须随附面向使用者的讲解，说明每个模块为什么需要、如何定制、如何删除。讲解与模板自身的介绍、选型清单、起步清单、维护说明、许可证声明和变更记录共同构成"起步引导层"：这一层必须明确标注为模板内容，不得妨碍生成仓库的正常使用，并且可以一步移除；移除后，其余文件中不得留下指向这一层的失效引用。
- **FR-013**: 每个推荐和可选模块都必须能单独删除，删除后其余模块照常工作。说明文档必须列出每个模块的删除方法和删除后的影响。
- **FR-014**: 可选模块在默认状态下不得产生可见的副作用，由使用者按说明启用。"可见的副作用"指在 GitHub 仓库页面或协作流程中出现的效果，例如赞助按钮、自动审阅请求、额外的检查或机器人评论。只影响本地编辑器格式的设置不在此列，但不得与模板自身的文本格式约定冲突；沿用上游通行做法而比模板自身更宽松（例如对 Markdown 行尾空格的放行）不算冲突，因为模板自身的文件仍受更严格的约定约束。

**核心模块的行为**

- **FR-015**: 忽略规则默认必须覆盖常见操作系统和编辑器产生的文件，并说明如何按项目语言从选定来源补充对应规则。
- **FR-016**: Issue 入口必须提供"缺陷报告"和"功能建议"两个结构化表单，关键字段必填；空白 Issue 默认关闭；并提供把使用求助引到其他渠道的链接。
- **FR-017**: 合并请求模板必须预先填好变更说明、关联 Issue 和自检清单（测试、变更日志、文档三项）。
- **FR-018**: 变更日志必须遵循 Keep a Changelog 格式和语义化版本（SemVer）。生成仓库默认使用平台自动生成的发布说明，并按"新功能 / 修复 / 其他"分类。选型清单必须按项目类型推荐变更日志自动化工具（Node 项目、非 Node 项目、需要自动发起发版合并请求的项目），但默认不启用任何一种。
- **FR-019**: 安全策略必须说明受支持的版本范围和私下报告漏洞的方式，明确要求不要公开提交漏洞，并提供私有漏洞报告功能未开启时的备用联系方式。
- **FR-020**: 行为准则必须采用 Contributor Covenant 的某个正式版本，举报联系方式使用占位符，并保留上游要求的署名。
- **FR-021**: 贡献指南必须至少说明如何提交 Issue、如何提交合并请求（复刻、建分支、提交、发起请求），以及代码风格和测试要求。
- **FR-022**: 自动检查必须在推送到默认分支、发起以默认分支为目标的合并请求时触发，在还没有代码的生成仓库上也能成功运行，并清楚标出接入语言相关检查和测试的位置（安全要求见 FR-039）。
- **FR-023**: 依赖自动更新默认必须管理自动检查所用动作（actions）的版本，并说明如何按项目语言增加其他依赖生态。
- **FR-024**: 生成仓库的许可证默认使用 MIT。许可证文件使用标准 MIT 文本，GitHub 据此识别出 SPDX 标识 `MIT`；选型清单也用 SPDX 标识记录许可证。说明文档必须告诉使用者如何改用其他许可证。

**选型依据与信任**

- **FR-025**: 模板必须提供一份独立的选型清单文件，覆盖全部模块。每个条目包含：模块名称、对应文件、级别、选定来源（附链接）、上游许可证、认可度证据、数据核实日期、入选理由，以及考虑过的备选方案。
- **FR-026**: 认可度证据必须如实标注类型：精确 Star 数、四舍五入的 Star 数、估算使用人数、平台官方功能、事实标准（附具体采用者）或"未取得"。不得编造数字。
- **FR-027**: 模板首页必须以摘要表展示各模块的来源和认可度，并在一次点击内通往完整的选型清单。
- **FR-028**: 生成仓库中每个模块的文件都必须带一行来源注释，至少写明上游来源名称和链接（适用时附版本）。注释在渲染后的页面上不可见，也不影响文件的正常使用。加注释会影响平台识别或正常使用的文件（如许可证文件）不加注释，改由选型清单追溯。
- **FR-029**: 选型必须遵循并公开以下规则：
  1. 先看社区认可度，包括 Star 数、被成功项目实际采用的程度、是否已成为事实标准；只看 Star 数不够。
  2. 认可度相当时，选择对仓库持有者更容易起步的方案。
  3. 多个选项同样合格时，可以按作者个人偏好选择，并在条目中注明。
- **FR-030**: 选型清单必须列出被刻意排除的知名候选及排除理由，至少包括：非官方却以"标准"自居的目录布局项目（Star 数高但不权威的反例），以及已被平台原生功能取代的旧模板合集。
- **FR-031**: 必须逐一核对上游来源的许可证，并记录在选型清单中。收录或改写的上游内容必须按其许可证要求保留署名。

**平台特性说明**

- **FR-032**: 说明文档必须介绍如何用账号级 `.github` 仓库下发默认社区健康文件，并明确说明两条规则：一是生成仓库自带的 Issue 表单会让账号级默认 Issue 模板整体失效；二是许可证不能由账号统一下发。

**维护与数据时效**

- **FR-033**: 模板必须提供维护说明，内容包括：认可度数据的复核周期（至少每 6 个月一次，且每次发布新版本前都要复核）、复核步骤，以及触发重新评估的条件：上游末次提交超过 12 个月（以默认分支最近一次提交为准，仓库已归档视同满足）、依赖已被广泛弃用的工具、出现认可度明显更高的新候选。
- **FR-034**: 模板必须维护自身的变更记录，写明每个版本中选型的新增、替换和移除，以及各自的原因。
- **FR-035**: 模板仓库自身必须通过 GitHub 社区标准自检页的全部检查项，并在设置中标记为模板仓库。

**模板自身的发布属性**

- **FR-036**: 模板仓库自身以 MIT 许可证发布，同时必须满足 FR-010：生成仓库中的许可证文件不得以生效状态包含模板作者的版权署名。说明文档必须声明：从本模板生成的项目无需保留模板作者的署名，可以自由替换版权人或改用其他许可证。
- **FR-037**: 模板自身的说明文档（首页介绍、选型清单、起步清单、讲解和维护说明）必须使用中英双语。生成仓库中的协作文件（项目说明骨架、Issue 表单、合并请求模板、贡献指南、安全策略、行为准则等）及其中的来源注释使用英文。说明文档应指出可用的上游官方中文译本，方便中文项目自行替换。
- **FR-038**: 模板仓库必须使用以下标题、简介和主题标签，便于被搜索和识别：
  - 首页（README）标题：Chef's Pick OSS Starter · 主厨精选开源仓库起步模板
  - 简介（About，只用英文）：Chef's pick starter for open-source repos — community-proven best-of-breed essentials, ready to use.
  - 主题标签（Topics）：template、starter、open-source、best-practices、community-health、github-template

**自动化安全基线**

- **FR-039**: 生成仓库的自动化配置（自动检查、依赖自动更新）引用的每个 GitHub 动作，都必须固定到完整的提交哈希，并在同一行注明对应的版本号；依赖自动更新必须覆盖这些引用，让哈希随新版本定期升级。工作流令牌默认只有只读权限，只有确实需要的步骤才单独提升权限。说明文档必须解释这样做的原因，并说明使用者新增动作时如何照做。

### Key Entities *(include if feature involves data)*

- **模块（Module）**：仓库的一个核心要素，如行为准则。属性包括：名称、级别（必需、推荐、可选）、对应文件、选定来源、备选来源、删除方法及影响。
- **来源（Source）**：模块内容或所遵循规范的上游出处。属性包括：名称、链接、类型（开源仓库、平台官方功能、规范网站）、许可证、维护状态、最近活跃时间。一个模块有一个选定来源，可以有多个备选来源。
- **认可度证据（Adoption Evidence）**：支撑"佼佼者"判断的数据。属性包括：证据类型（精确 Star 数、四舍五入 Star 数、估算使用人数、官方地位、事实标准及采用者举例、未取得）、数值或描述、数据出处、核实日期。每个来源至少有一条证据。
- **选型决定（Selection Decision）**：记录某模块为什么选了某来源。属性包括：适用的选型规则（认可度优先、起步容易、作者偏好）、备选方案、被排除的候选及理由、复核状态（有效、需重新评估）。
- **排除的候选（Excluded Candidate）**：被刻意排除的知名候选。属性包括：来源、认可度证据、排除理由（FR-030）。
- **占位符（Placeholder）**：生成仓库中需要使用者替换的项目身份信息。属性包括：统一标记、含义、出现位置、替换示例。
- **起步步骤（Setup Step）**：生成仓库后需要完成的一项操作。属性包括：顺序、说明、必做或选做、完成后的验收方式。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 首次使用的开发者从生成仓库到完成起步清单全部必做步骤，用时不超过 15 分钟（观察指标，不作为发布门槛，见 Assumptions 中的"验证方式"）。
- **SC-002**: 完成起步清单后，生成仓库在 GitHub 社区标准自检页上的检查项 100% 显示为已完成。
- **SC-003**: 交付的模块 100% 在选型清单中具备来源、认可度证据（或"未取得"标注加替代证据）、核实日期和入选理由。
- **SC-004**: 访问者从模板首页出发，一次点击内即可到达选型清单，并能直接定位到任一模块的条目。
- **SC-005**: 未做任何修改的新生成仓库，首次自动检查的通过率为 100%。
- **SC-006**: 完成起步清单后，仓库中剩余的占位符为 0 个，处于生效状态（定义见 FR-010）的模板作者身份信息为 0 处。
- **SC-007**: 逐一删除每个推荐或可选模块后，其余模块照常工作、自动检查仍然通过，逐项验证的通过率为 100%。
- **SC-008**: 任一时刻，选型清单中所有认可度数据的核实日期距当天都不超过 6 个月；每次模板发布时，所有数据的核实日期都不早于发布前 30 天。
- **SC-009**: 访问者能在 2 分钟内说出任一指定模块的选定来源和入选理由（观察指标，不作为发布门槛，见 Assumptions 中的"验证方式"）。
- **SC-010**: 新生成的仓库在默认状态下，由可选模块引起的可见副作用为 0 项（如无效的赞助按钮、指向不存在账户的审阅请求）。
- **SC-011**: 外部贡献者从进入生成仓库到提交一份完整的缺陷报告，用时不超过 5 分钟（观察指标，不作为发布门槛，见 Assumptions 中的"验证方式"）。
- **SC-012**: 新生成的仓库中，未固定到完整提交哈希的动作引用为 0 处，默认带写权限的工作流令牌为 0 个。

## Assumptions

- **平台**：本模板面向 GitHub，依赖其模板仓库、社区健康文件、Issue 表单、自动生成发布说明、Dependabot、Actions 和私有漏洞报告等原生能力。其他代码托管平台不在本期范围内。
- **目标使用者**：具备基本的 Git 和 GitHub 操作能力。
- **验证方式**：作者会在发布后马上用本模板起步自己的项目，在使用中观察 SC-001、SC-009、SC-011 这类体验指标，发现的问题记录下来，在后续版本中改进。这几项不作为发布门槛，其余成功标准都是发布门槛。
- **选型基线**："五脏俱全"核心清单和目标目录结构以报告 2（修订版）的个人小项目方案为准；团队级和基金会级内容（报告 1）只用于可选的升级指引。各模块的候选来源和认可度数据见 [input.md](./input.md) 第 5 节及两份报告（核实日期 2026-09-17）。实施前须重新核实数字和维护状态，并更新核实日期。
- **生成仓库的默认许可证**：MIT（交接文档已确定）。
- **行为准则版本**：规划阶段已按选型规则选定 Contributor Covenant 2.1，理由见 [research.md](./research.md) 中的 R4。
- **变更日志自动化**：changesets、git-cliff、release-please 只作推荐，默认不启用；个人项目默认使用平台自动生成的发布说明。
- **仓库设置无法随文件下发**：开启私有漏洞报告、开启讨论区、填写仓库简介、标记模板仓库等都属于仓库设置，不能随模板文件自动生效，只能通过起步清单引导使用者手动完成。
- **不包含**：团队版模板（团队级增强只在可选的升级指引中介绍）、语言相关的项目脚手架（选型清单也不推荐；input.md 第 5.4 节的内容不采用）、脚手架生成器（如 cookiecutter、copier）、其他代码托管平台，以及已生成仓库与模板之间的自动同步。
