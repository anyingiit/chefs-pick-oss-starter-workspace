# Feature Specification: 英文为主、中文另起一份的文档语言结构

**Feature Branch**: `002-english-first-docs`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "我认为以英文为主的文档能够显著提高社区认可度、使用意愿和维护意愿，我确实要求中英双语，但是这种一行中文一行英文的效果不是我想要的，我想要的是默认英文，以英文为主，然后提供一个链接指向到中文文档，我认为这是社区的共识做法，也能拓宽不同语言使用者的国家边界。我需要你先去证实我的猜测是否正确。"

## 背景与取证结论 *(本节是本规格的事实依据)*

现状：模板的起步引导层（`.github/README.md` 与 `.github/chefs-pick/` 下 6 份文档，合计约 119 KB）采用**同文档内逐段中英并排**，每个标题写成「中文 / English」，每段中文后紧跟一段英文。任何一种语言的读者都要跳过约一半内容才能读完。

取证范围：25 个仓库的一手文件（浅克隆后直接读取根树与 README 原文），分三类——模板 16 个模块的选定来源、超高使用量/活跃度仓库、以及近年快速积累使用者与维护者的新项目（含大量中文起源项目）。

结论：**用户的判断成立，且证据强度高于预期。**

1. **无一例外的英文规范版本。** 25 个样本的根 `README.md` 正文中文占比为 0.0%–0.6%（残余仅为语言入口链接与个别专有名词）。其中中文起源项目全部如此：dify、RAGFlow、LobeChat、思源笔记、GPT-SoVITS、DeepSeek-V3、Ant Design、Element Plus、ECharts、gin、RustDesk、PDFMathTranslate。
2. **逐段并排的做法在样本中出现 0 次。** 对 20 个仓库的 README 做交替段落检测，命中数为 0。检索到的"中英逐段对照"实例仅来自翻译工具自身的演示，以及小型项目；即便这些项目的改造合并请求，目标写法也是"English front page + 简体中文 + 语言切换"。
3. **共识形态是"规范英文 + 语言入口 + 独立译本文件"**，写法有三种等价变体：行内链接（`English | [简体中文](docs/README_zh-CN.md) | …`，PDFMathTranslate；`… · English · [中文](./README-zh_CN.md)`，Ant Design）、徽章行（RAGFlow，11 种语言）、方括号列表（RustDesk，26 种语言）。译本文件本身是单语的（思源 `README.zh-CN.md` 中文占比 38.9%，英文版 0.0%）。
4. **模板自己挑中的"佼佼者"就是这样做的。** Best-README-Template、Contributor Covenant、GitHub Open Source Guides、Keep a Changelog、SemVer 的仓库 README 全部为纯英文；译本一律另置：Contributor Covenant 放在 `content/version/2/1/code_of_conduct.zh-cn.md` 并配语言选择器；opensource.guide 用 `_articles/<lang>/` 与 `_data/locales/<lang>.yml`，其 `docs/translations.md` 明确规定英文是源、译本随后跟进；SemVer 的 README 指向 semver.org 的"localized specifications"。
5. **协作文件通常不翻译。** 15 个样本中 11 个的 CONTRIBUTING / CODE_OF_CONDUCT / SECURITY 译本数为 0。这支持现行"生成仓库中的协作文件用英文"的规定保持不变。

对"显著提高认可度与参与意愿"这一因果判断的保留：本次取证得到的是**一致的显示性偏好**（所有高认可度、高活跃度、快速增长的项目都选择了英文规范版本），而不是对照实验。规格按"这是社区共识做法"立论，不主张已被量化验证的因果效应。

## Clarifications

### Session 2026-09-18

- Q: 六份面向使用者的模板文档里，哪几份要配中文译本？ → A: 首页 + 起步清单两份（约 18 KB）；其余四份只提供英文版
- Q: 当中文译本落后于英文原文时，应该由哪一道检查拦住它？ → A: 结构由日常校验硬失败；内容新鲜度靠译本中的来源标记，日常仅提示、发布门禁硬失败
- Q: 那四份只有英文版的文档，顶部还要不要放语言入口？ → A: 不放，也不加任何说明。英文是主要语言，中文只是译本；英文文档本身就是英文的，无需声明，只有部分实用文档附带中文
- Q: 中文文档里指向只有英文版的文档的链接，还要不要预告「目标是英文」？ → A: 不要，删除该要求。同一条原则对称适用：落到英文是默认情形，逐链接声明属于噪音；定位信息由译本顶部的规范性声明承担
- Q: 起步清单里的占位符登记表，中文版要不要跟着复制一份？ → A: 不复制。中文版保留该章节，但指向英文原文中的唯一一张登记表，只用中文解释怎么用它
- Q: 中文版和英文原文的「章节集合一致」，要靠什么来比对？ → A: 每个标题前加不可见的 HTML 注释锚点，中文标题全译，校验按锚点 id 集合比对
- Q: 001 逐字契约里那 12 处认可度数字漂移，算不算本功能要修的范围？ → A: 算。同步那 12 个数字，并增加一项校验保证契约与 `template/` 的认可度数字不再漂移

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 英文读者读到一份纯英文的模板首页 (Priority: P1)

一位不懂中文的开发者打开模板仓库。首页是一份完整、连贯、不含中文散文的英文介绍：模板给了什么、怎么选的、怎么开始。页面顶部有一行语言入口，中文读者可从这里离开。

**Why this priority**: 这是整个改动的目的。模板面向的是全球开源协作场景；首页决定陌生访客是否继续读下去，而现状让英文读者在每一段都撞上读不懂的内容。

**Independent Test**: 只改造首页即可独立验收——取 `.github/README.md`，检查正文（语言入口行之外）不含任何中文字符，且内容自洽、不依赖中文段落才完整。

**Acceptance Scenarios**:

1. **Given** 一位英文读者打开模板仓库首页，**When** 他从头读到尾，**Then** 除顶部语言入口中的语言名称外，他不会遇到任何中文散文，也不会遇到需要中文才能理解的内容缺口。
2. **Given** 首页顶部的语言入口，**When** 读者点击中文入口，**Then** 他到达对应的中文首页，且中文首页顶部有指回英文首页的入口。
3. **Given** 任意一份面向使用者的模板文档，**When** 检查其标题行，**Then** 标题为单一语言，不再是「中文 / English」的并排写法。

---

### User Story 2 - 中文读者读到一份纯中文的完整文档 (Priority: P2)

一位中文开发者从语言入口进入中文版本。中文版是一份独立完整的文档，不是英文版的摘要，也不需要在中英之间跳读。

**Why this priority**: 用户明确要求保留中英双语能力。译本如果只是残缺摘要，等于取消了双语；但它的优先级低于 P1，因为英文版本身就是完整交付物。

**Independent Test**: 取中文版文档，检查其散文部分不含英文句子（技术标识符、命令、文件名、产品名除外），且它覆盖英文原文的全部章节——单一数据源的内容按 FR-011 引用而非复制，不算缺章节。

**Acceptance Scenarios**:

1. **Given** 一位中文读者进入中文首页，**When** 他从头读到尾，**Then** 他获得与英文首页同等的信息量，且不需要回到英文版补齐任何内容。
2. **Given** 中文版中的每一个内部链接，**When** 读者点击，**Then** 目标文档有中文版时落到中文版；没有中文版时落到英文版，不附加任何逐链接提示。
3. **Given** 一份中文译本落后于英文原文，**When** 读者打开它，**Then** 文档顶部明确告知英文是规范版本，并给出英文原文的链接。

---

### User Story 3 - 维护者不会让译本悄悄失效 (Priority: P3)

维护者修改英文原文后，有明确规则和自动校验保证中文版不会无声地过期，发布前也有门禁兜底。

**Why this priority**: 双语的真实成本在维护，不在首次撰写。没有这条，译本会在两三次改动后变成错误信息，比没有译本更糟。但它不阻塞前两个故事的交付。

**Independent Test**: 在英文文档中增加一节而不动中文版，运行校验，应当有一项失败并指出是哪份译本、哪一节缺失。

**Acceptance Scenarios**:

1. **Given** 英文文档新增或删除了一个章节，**When** 运行结构校验，**Then** 校验报告指出对应中文译本的章节集合与英文不一致。
2. **Given** 任意一份文档，**When** 运行结构校验，**Then** 校验会拒绝"英文文档正文含中文散文"或"中文文档正文含英文散文"的情况。
3. **Given** 准备发布，**When** 运行发布门禁，**Then** 门禁逐项确认每份译本都与当前英文原文对齐。

---

### User Story 4 - 使用者学会给自己的项目做同样的事 (Priority: P3)

模块讲解告诉使用者：如果你的项目要面向中文用户，惯例做法是保持 `README.md` 为英文、另起一份中文 README、并在顶部放语言入口——并给出可直接抄用的写法。

**Why this priority**: 这是取证过程中浮现出来的、对使用者真正有用的知识，且与模板"把社区共识挑好拼好"的定位一致。但它是附加价值，删掉不影响前三个故事。

**Independent Test**: 取模块讲解中的对应小节，按其指引可在一个空仓库里落地一套"英文 README + 中文 README + 语言入口"，不需要额外查资料。

**Acceptance Scenarios**:

1. **Given** 使用者读完该小节，**When** 他照做，**Then** 他得到一份英文 README、一份中文 README 和一行可用的语言入口，且两份文档互相可达。
2. **Given** 该小节，**When** 使用者查看它推荐的做法，**Then** 每条建议都注明了依据（哪些广泛采用的项目这样做），而不是凭空的风格主张。

---

### Edge Cases

- 中文译本落后于英文原文时，读者与维护者各自如何得知？（要求：读者一侧由译本顶部的规范性声明承担，不得读完之后才发现；维护者一侧由来源标记与日常校验的提示承担。）
- 使用者执行清理命令后，中文文档必须与英文文档一并消失，且生成的项目里不得残留任何指向模板文档的语言入口或失效链接。
- GitHub 的社区标准自检页与仓库首页渲染只认 `README.md`；新增的中文文件不得改变首页的渲染结果，也不得让自检项退化。
- 机器可读的数据（认可度数据表等）如果在中英两份文件里各存一份，必然漂移；这类内容只能有一个存放位置。
- 语言入口本身含有"简体中文""日本語"这类非英文字符串——语言纯度校验必须允许这一处例外，否则规则无法落地。
- 中文文档中的代码块、命令、文件名、产品名与许可证标识必然是英文，不能被当作"混入英文散文"。
- 中文读者从中文首页或中文起步清单出发，链接会把他带进只有英文版的模块讲解、选型清单与维护说明。这是预期行为，不逐条预告；读者的定位由译本顶部的规范性声明承担。
- 起步清单被翻译后，其中的占位符登记表是最容易被顺手复制的一节；一旦复制，两张表就会各自演化出第二套名称或示例。全模板必须只有一张登记表。
- 章节锚点必须渲染后不可见，否则读者会在正文里看到一串标识；它也不能被当作「中文文档里混入英文」而被语言纯度校验判失败。
- 英文原文增删一个章节而忘了同步锚点，会让比对失去依据；锚点的增删必须与章节本身绑定，只有英文原文与译本同时更新才算完成。
- 认可度数据刷新只回写 `template/`，逐字契约无人同步——这正是那 12 处漂移的成因。新增的防复发校验必须在刷新之后仍然能发现差异，而不是只在人工编辑时才生效。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 面向使用者的模板文档必须以英文为规范版本（canonical）。发生歧义或译本滞后时，以英文版为准，这一点必须在译本中对读者写明。
- **FR-002**: 每一份面向使用者的模板文档，其任意一个语言版本都必须是**单语**的：英文版的散文中不得出现中文，中文版的散文中不得出现英文句子。代码、命令、文件名、标识符、产品名、许可证标识、章节锚点、以及语言入口中的语言名称不受此限。
- **FR-003**: 禁止在同一文档内逐行或逐段并排两种语言，标题、表头、列表项、单元格同样适用。
- **FR-004**: 语言入口只出现在拥有一个以上语言版本的文档上：顶部一行，列出该文档全部可用语言，当前语言以纯文本呈现，其余语言为链接，写法在这些文档之间保持一致。只有英文版的文档不放语言入口，也不加任何关于语言的说明——英文是主要语言，文档本身即英文，无需声明。
- **FR-005**: 语言入口必须双向可达：从任一语言版本出发，都能一步到达同一文档的其他任一语言版本。
- **FR-006**: 中文译本的覆盖范围限定为**模板首页**与**起步清单**两份文档。模块讲解、选型清单、维护说明、模板变更记录只提供英文版，不带语言入口。后续扩大覆盖范围不需要改变结构，只需新增译本文件并为该文档加上语言入口。
- **FR-007**: 凡提供了中文版的文档（见 FR-006），中文版必须覆盖其英文原文的全部章节，不得是摘要或节选。章节必须齐全，但其中属于 FR-011 所指单一数据源的内容按 FR-011 引用而非复制——这不算缺章节。为使章节可被跨语言比对，这些文档的每一个标题前必须放一个语言无关的章节锚点：渲染后对读者不可见，各语言版本中逐字相同，且不随标题被翻译。
- **FR-008**: 语言入口只能列出确实存在的语言版本，不得产生指向不存在文件的链接。
- **FR-009**: 生成仓库中交付给使用者的文件仍然全部使用英文，本功能不向生成的仓库新增任何中文文件。
- **FR-010**: 起步引导层（含其全部语言版本）必须仍然可以一步移除；移除后不得留下任何失效链接、语言入口残片或孤立的中文文件。
- **FR-011**: 由工具批量刷新或逐项核对的结构化数据——认可度数据表、占位符登记表等——在整个模板中只能存在一份，且位于英文原文中。其他语言版本保留对应章节，但指向那唯一一份数据并用本语言解释如何使用它，不得复制出第二份。理由是这类内容由标识符、路径和数值构成，本就不该翻译；复制只会制造可漂移的副本，并迫使校验同时核对多处。
- **FR-012**: 每一份译本必须记录它所依据的那一版英文原文（来源标记），使「译本是否已跟上原文」成为可机读、可比对的事实，而不是一句人工声明。英文原文变更后，要么在同一次变更中更新译本并推进来源标记，要么让来源标记停留在旧值，以此显式表示尚未跟进。
- **FR-013**: 日常结构校验必须自动判定下列各项，并在不满足时**直接失败**：每份文档的语言纯度、语言入口的存在与互指、中英章节集合是否一致（按 FR-007 的章节锚点 id 集合比对，而非标题文本）、以及清理后无残留。章节不一致时，报告必须指出是哪一份译本缺少或多出哪一个锚点。这些都是确定性可判定的，不允许以提示形式放过。
- **FR-014**: 内容新鲜度（译本的来源标记是否指向当前英文原文）在日常校验中只作**提示**，不使校验失败；但它必须在发布门禁中**硬失败**。区别对待的理由是：正文语义是否仍然准确无法自动判定，日常硬失败只会逼出敷衍的译文。
- **FR-015**: 发布门禁必须包含一项：全部译本与当前英文原文对齐，即章节集合一致、语言入口双向可达、无指向不存在译本的链接、且全部来源标记都指向当前英文原文。
- **FR-016**: 模块讲解必须告诉使用者如何为自己的项目落地同样的多语言 README 做法，并注明依据。此项替代现有的"中文译本"链接表格，原表格中的官方译本链接需保留在新写法中。
- **FR-017**: 改造后的文档在语言纯度之外，仍须满足现行的全部结构约束：占位符不进入引导层（起步清单的登记表除外）、链接使用相对路径、`tools/` 只以行内代码出现、Star 数格式统一。
- **FR-018**: 本功能重写逐字契约时，必须一并消除契约与 `template/` 之间既有的 12 处认可度数字差异，并增加一项自动校验，使两者的认可度数字此后不再漂移。只补数字不堵成因是不够的：漂移的根源是数据刷新只回写 `template/`、契约无人同步、且现有校验完全不覆盖契约，因此下一次刷新会立刻重现。

### Key Entities

- **文档 (Document)**: 一份面向使用者的模板说明，例如模板首页、起步清单、模块讲解、选型清单、维护说明、模板变更记录。它有且只有一个规范语言版本（英文）。
- **语言版本 (Language edition)**: 某份文档在某种语言下的完整内容，单语呈现，独立成文件。译本对规范版本有从属关系与同步义务。
- **语言入口 (Language selector)**: 文档顶部列出该文档全部语言版本的一行导航，是各语言版本之间唯一的跳转方式。
- **规范性声明 (Canonical notice)**: 译本中告知读者"英文版为准"并给出英文原文链接的固定内容。
- **来源标记 (Source marker)**: 译本中记录其所依据的那一版英文原文的标识。它让「译本是否跟上原文」可被机器比对，是 FR-012、FR-014、FR-015 共同依赖的事实来源。
- **章节锚点 (Section anchor)**: 标题前的语言无关标识，渲染后不可见，在同一文档的各语言版本中逐字相同。它让「章节集合是否一致」不依赖标题文本，因而不受翻译影响。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 模板仓库首页的英文正文中，中文字符数为 0（语言入口行除外）；当前该文件中文字符数为 1,034。
- **SC-002**: 全部面向使用者的模板文档，其英文版中文字符数合计为 0；当前 7 份文档合计 12,502 个中文字符散布在英文段落之间。
- **SC-003**: 英文读者读完模板首页所需跳过的不可读内容占比从目前的约一半降为 0。
- **SC-004**: 中文读者读完中文首页所需跳过的不可读内容占比同样为 0。
- **SC-005**: 从任一语言版本到达同一文档的其他任一语言版本，点击次数不超过 1 次。
- **SC-006**: 首页与起步清单的中文版对其英文原文的章节覆盖率为 100%；其余四份文档的中文版数量为 0，且不含语言入口。
- **SC-007**: 执行一步清理命令后，仓库中与模板文档相关的残留文件数为 0，失效链接数为 0。
- **SC-008**: 语言纯度、语言入口互指、中英章节一致性、清理后无残留这四项，100% 由日常自动校验覆盖并在不满足时直接失败，不依赖人工检查。
- **SC-009**: 改造后模板仓库首页的英文版篇幅不超过现有双语版篇幅的 60%，且信息不减少。
- **SC-010**: 发布门禁项数增加不超过 1 项，维护者的发布前人工检查步骤不增加。
- **SC-011**: 译本内容新鲜度 100% 由来源标记表示，发布前无需人工逐句比对中英正文即可判定是否对齐。
- **SC-012**: 占位符登记表与认可度数据表在整个模板中各只存在 1 份，新增语言版本不会使这个数字增加。
- **SC-013**: 章节集合不一致时，校验 100% 能指名是哪一份译本、哪一个章节锚点出了问题，不需要人工逐节对照；章节锚点在渲染后的可见字符数为 0。
- **SC-014**: 逐字契约与 `template/` 之间的认可度数字差异数为 0（当前为 12 处），且这一差异由自动校验覆盖，刷新一次认可度数据后差异仍为 0。

## Assumptions

以下为在用户描述未指定处所采用的合理默认，可在 `/speckit-clarify` 中调整：

- **译本覆盖范围**：已在 Clarifications 中定案，写入 FR-006，不再是假设——只译首页与起步清单。依据有二：宪章 2.1.0 新增的发布门禁 6 让每一份译本都变成每次发布必须逐项核对的硬成本；取证样本中 dify、RAGFlow、LobeChat、思源也都只翻 README 或 README 加站点文档，深层参考文档留在英文。
- **文件命名**：采用 BCP 47 后缀形式 `<NAME>.zh-CN.md`，这是样本中最常见的写法（LobeChat、思源笔记）。其余等价写法（`-zh_CN`、`_zh`、`docs/<lang>/`）不再混用。
- **存放位置**：中文版与其英文原文放在同一目录层级，以保证"一步清理"命令不需要枚举更多路径。首页的中文版如何安置需在规划阶段确认，判据是清理命令不得从一条变成多条。
- **语言入口写法**：采用行内文本链接（当前语言为粗体纯文本，其余为链接），不采用徽章图片——徽章会引入外部图片依赖，与模板"零依赖"的取向冲突。入口只出现在哪些文档上已在 Clarifications 中定案，写入 FR-004，不再是假设。
- **译本滞后策略**：已在 Clarifications 中定案，写入 FR-012 至 FR-015，不再是假设——英文先行、译本跟进；结构由日常校验硬失败，内容新鲜度由来源标记表示、日常仅提示、发布门禁硬失败。来源标记的具体形式（提交哈希、内容摘要或版本号）留给规划阶段，判据是能被工具比对，且改动英文原文时不容易忘记推进它；它可以沿用章节锚点那种渲染后不可见的写法。
- **语言范围**：本功能只做英文与简体中文两种。新增更多语言不在范围内，但结构设计不应阻断后续扩展。
- **开发过程文件**：规格、规划、契约、宪章等继续使用中文，不受本功能影响。
- **生成仓库**：不新增任何中文文件，也不改变现有协作文件的英文内容——取证显示 15 个样本中 11 个根本不翻译协作文件。

## Dependencies

- **宪章修订（已解除）**：原宪章「附加约束 · 文档语言」规定"面向使用者的模板说明文档必须使用中英双语"，与本功能字面冲突。该条已由宪章 v2.0.0 改为"英文为规范版本，中文以独立译本文件提供，配统一的语言入口"，v2.1.0 又补上发布门禁第 6 项"全部译本与当前英文原文对齐"。宪章检查不再阻塞。
- **既有契约与校验**：`specs/001-chefs-pick-starter/contracts/guidance-layer.md` 的逐字约定、`tools/check_template.py` 的 C11/C14/C17/C22 需要随之改写。
- **前一功能的遗留问题**：001 的逐字契约与 `template/` 之间已有 12 处认可度数字漂移。已在 Clarifications 中定案纳入本功能范围，写入 FR-018——同步数字并增加防复发校验，避免在新结构上复制同一个问题。

## Out of Scope

- 英文与简体中文以外的语言。
- 生成仓库内协作文件的翻译。
- 自动翻译或机器翻译流水线。
- 模板文档的内容改写——本功能只改语言结构，不借机重写论述。
