# Phase 0 调研：工作区自身遵守模板定下的规矩

每条都记「判定 / 理由 / 否决的替代方案」。凡涉及仓库现状的数字均为实测。

## R1 正确的发布流程是什么

**判定**：区分两种情形写。首次发布到**空仓库**时，`git subtree split` 与直接复制都可用，现状不变；后续发布到**已有内容的仓库**时，唯一安全的做法是**在模板仓库的克隆里替换内容后追加提交**，推送必须是快进。

**理由**（2026-09-18 实测）：模板仓库现有历史是 `51a8df8` → `99cba97` 两个提交，而 `git subtree split --prefix=template` 在当前工作区历史上切出的是 `26ec6b3` → … → `eff8648` 六个合成提交，两者**没有共同祖先**，`git merge-base --is-ancestor 99cba97 publish` 返回否。因此 `git push publish:main` 是非快进，照 README 字面执行只能加 `--force`。而模板仓库上有标签 `v1.0.0` 指向 `99cba97`：强推一个不含该提交的历史，会让这个标签指向任何分支都不可达的提交，`v1.0.0` 发布随时可能被回收。

`subtree split` 的合成提交哈希取决于历史上触及 `template/` 的提交集合，工作区历史一旦变动（合并提交、变基、压缩）就会重新生成一套，与模板仓库上一次发布的结果对不上。也就是说，这不是一次偶发，而是这条路径的固有性质。

**否决的替代方案**：
- 强推并接受标签失效——不可接受，会破坏已发布的版本。
- 先把模板仓库历史改写成 subtree 形状再沿用原流程——对公开仓库改写历史，代价远大于收益。
- 用 `git subtree push`——同样基于 split，问题一模一样。

## R2 后续发布的具体步骤

**判定**：写成五步，每步都可复制执行：
1. `git fetch` 模板仓库的默认分支，确保本地克隆是最新的。
2. 在克隆中检出默认分支。
3. 用工作区 `template/` 的内容整体覆盖克隆的工作树（保留 `.git`），使两者逐字节一致。
4. `git add -A`，提交。
5. 推送；这一步必须是快进，若被拒绝说明模板仓库上有工作区没有的提交，此时**停下来排查**，不要加 `--force`。

**理由**：第 3 步之后用「克隆的工作树与工作区 `template/` 逐字节相同」作为可验证的中间状态，维护者不必相信流程本身是对的，可以当场核对。第 5 步显式禁止 `--force` 并给出被拒时的处置，正是 R1 那类事故的拦截点。

**否决的替代方案**：`rsync --delete` 一步到位——本环境无 `rsync`，且它会因不认识 `.git` 而需要额外排除参数，容易写错；用 `cp -a` 覆盖加 `git add -A` 即可，因为 `git add -A` 本身就会登记删除。

## R3 校验如何延伸到 `template/` 之外

**判定**：新增检查项，路径从**仓库根**解析，并刻意忽略 `ctx.template_dir`；算法函数一律复用现有的，不复制。

**理由**：现有 24 项检查全部以 `ctx.template_dir` 为根，工作区 README 不在其下。C23 已立下先例——它用 `repo_root = Path(__file__).resolve().parent.parent` 解析契约与 `template/`，并在文档字符串里写明「never to `--template-dir`」。沿用同一模式，既不触碰任何既有检查的判定（FR-016），也不需要第二条命令（FR-015）。

可复用的现成件：`strip_for_purity()`、`cjk_count()`、`longest_english_run()`、`ANCHOR_RE`、`DIGEST_RE`、`hashlib.sha256(...).hexdigest()[:16]`、`WarnCheck`。新检查只写编排，不重写算法，这样 FR-014「与模板译本同一套判定」在实现层面就是字面成立的。

**否决的替代方案**：
- 把 C11／C24 改成接受「文档集合」列表——改动面大，直接威胁 FR-016 与 SC-011（既有 24 项判定必须逐项不变）。
- 用不同的 `--template-dir` 跑第二遍——工作区根不是模板，C01 等检查会立刻误报。
- 单独一个 `check_workspace.py`——违反 FR-015，维护者要记两条命令。

## R4 新增哪几项检查

**判定**：三项，编号续至 C25 ~ C27，总数 24 → 27。

| 编号 | 名称 | 判定内容 | 失败方式 |
|---|---|---|---|
| C25 | Workspace language structure | 语言纯度、语言入口存在与互指、章节锚点序列一致、译本顶部的规范性声明 | 直接 FAIL |
| C26 | Workspace facts | 首页声明的可机读事实与仓库实际状态一致 | 直接 FAIL |
| C27 | Workspace translation freshness | 译本来源标记指向当前英文原文 | WARN，`--release` 下 FAIL |

**理由**：与 `template/` 侧的切分保持同构——C11 管结构、C24 管新鲜度、两者分开，是因为结构错误是确定性的而新鲜度不是（002 规格 FR-014 的立论）。工作区侧沿用同一切分，维护者不必学第二套心智模型。事实准确性是 `template/` 侧没有的新类别，单列 C26。

**否决的替代方案**：合并成一项 C25——会把「必须硬失败」和「只应提示」两种语义塞进同一个退出码，正是 002 刻意避免的。

## R5 工作区首页的章节锚点

**判定**：沿用 `<!-- anchor: id -->` 写法，锚点序列固定为 6 项：
`workspace`、`layout`、`common-commands`、`publishing`、`license`，外加首个标题的 `chefs-pick-oss-starter-workspace`。

**理由**：现有 README 有 5 个二级标题（目录结构、常用命令、发布、许可证）加 1 个一级标题，共 5 节。改造后新增「发布」一节要拆出首次／后续两种情形，但仍在同一节内，节数不变。锚点在渲染后不可见（SC-013 的同类要求），可跨语言逐字比对。

**否决的替代方案**：按标题文本比对——标题一经翻译就对不上，002 调研 R2 已否决过一次。

## R6 译本文件名与位置

**判定**：`README.zh-CN.md`，与 `README.md` 同处仓库根目录。

**理由**：与模板首页的 `.github/README.zh-CN.md` 同构，`TRANSLATION_FILENAME_RE` 现成可用（`^(?P<id>[A-Za-z-]+)\.(?P<lang>[a-z]{2}(-[A-Z]{2})?)\.md$`），无需新造命名规则。

## R7 新鲜度标记

**判定**：沿用内容摘要 `<!-- translation-of: README.md sha256:<16 hex> -->`，并让 `--update-digests` 一并覆盖工作区译本。

**理由**：与 002 调研 R3 同源——工作区与模板仓库之间提交哈希不通用，且工作区自身历史也会变动；内容摘要只依赖文件字节，改了原文摘要必变。让同一个 `--update-digests` 覆盖两侧，维护者不必记住「工作区的要另外刷」。

## R8 需要核对哪些事实、怎么核对

**判定**：三项，各用一条固定句式承载，英文版与中文版都要核对。

| 事实 | 实测当前值 | README 现写 | 核对方式 |
|---|---|---|---|
| `template/` 文件数 | 28 | 26 ❌ | 与 `git ls-files template/` 计数比对 |
| `specs/` 下的规格目录 | 001、002、003 | 只列 001 ❌ | 每个实际存在的目录都必须在首页出现 |
| 结构校验项数 | 改造后 27 | 24（改造前正确） | 与检查项注册表的长度比对 |

**理由**：这三项都是「每次迭代必然变化」的高漂移事实，正因如此才值得机器核对——留着不检查必然腐化（现状已有 2 处不符即为证据）。报错时同时给出声明值与实际值（FR-012），使修正不需要二次查找。

**否决的替代方案**：把这些数字从首页删掉以消除漂移源——省事，但等于用「不说」换「说得对」，与模板「把事实钉死并由机器核对」的一贯做法相反；而且目录结构表对首次接触本仓库的人确有价值。

## R9 `--update-digests` 与工作区的交互

**判定**：`update_digests()` 在处理完 `template/` 下的译本后，另行处理工作区根目录的译本，复用同一段替换逻辑（单处替换、写字节、拒绝重复标记）。

**理由**：该逻辑刚在 002 的评审轮中修过三个缺陷（原地替换、混合换行、重复标记），复用即继承修复；另写一份必然重蹈覆辙。
