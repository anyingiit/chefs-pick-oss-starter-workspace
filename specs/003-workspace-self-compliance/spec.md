# Feature Specification: 工作区自身遵守模板定下的规矩

**Feature Branch**: `claude/trusting-babbage-xq8avi`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "修掉 README 的发布流程，工作区也需要完全符合模板的精神。"

## 背景：两类问题，一个根源

功能 002 把**模板交付给使用者的那一层**改成了英文规范版 + 独立译本，理由是「一个推荐社区规范的模板，自己首先要遵守这些规范」。但改造范围止于 `template/`，工作区自身的门面没有动。

今天的一次真实发布暴露了第二类问题：工作区 README 写的发布流程是错的，照着做会损坏模板仓库的 `v1.0.0` 发布。

两者根源相同——**工作区不检查自己**。校验工具的 24 项检查全部只看 `template/`，工作区自己的文档既没有语言约束，也没有任何事实准确性约束，于是既写错了流程，也留着 002 要消除的中英并排写法。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 维护者照着 README 发布，不会毁掉已有发布 (Priority: P1) 🎯 MVP

维护者完成一轮改动后，打开工作区 README 的「发布」一节，照着上面的命令把 `template/` 同步到模板仓库。

**Why this priority**: 这是唯一会造成不可逆外部损坏的缺陷。其余各项都只是观感与一致性问题。

**Independent Test**: 在一个已有历史和标签的测试模板仓库上，完整执行 README 写的步骤，检查标签指向的提交是否仍可从默认分支到达。

**Acceptance Scenarios**:

1. **Given** 模板仓库已有若干次发布历史和至少一个版本标签，**When** 维护者照 README 的发布步骤操作，**Then** 推送成功，且原有全部提交与标签仍可从默认分支到达。
2. **Given** 模板仓库是刚建好的空仓库，**When** 维护者照 README 的发布步骤操作，**Then** 首次发布同样成功，文档明确区分了首次与后续两种情形。
3. **Given** 维护者按 README 操作到某一步失败，**When** 阅读该步骤的说明，**Then** 文档已事先写明这一步为何可能失败以及如何判断。

---

### User Story 2 — 外部访客看到的工作区门面是英文 (Priority: P2)

一位不读中文的开发者在 GitHub 上打开工作区仓库，想弄清这个仓库是什么、与模板仓库什么关系、怎么参与。

**Why this priority**: 工作区仓库是公开的，其首页承担与模板首页相同的「第一印象」职责。这正是 002 的立论，只是当时没有应用到自己身上。

**Independent Test**: 剥离代码块与语言入口后统计首页英文版的中文字符数，并确认页面信息自足。

**Acceptance Scenarios**:

1. **Given** 访客打开工作区仓库首页，**When** 通读全文，**Then** 不遇到任何中文散文，也没有需要中文才能理解的内容缺口。
2. **Given** 中文读者打开工作区仓库首页，**When** 需要中文，**Then** 顶部有一处写法与模板一致的语言入口，一步到达中文版。
3. **Given** 中文版与英文版并存，**When** 比对两版章节，**Then** 章节一一对应，中文版不是摘要或节选。

---

### User Story 3 — 工作区文档里的事实与仓库现状一致 (Priority: P2)

维护者或访客阅读工作区 README 里的目录结构表和数字，用它判断仓库里有什么。

**Why this priority**: 陈旧事实会把读者引向错误结论，且随每次功能迭代持续劣化。

**Independent Test**: 逐条比对文档中可机读的事实与仓库实际状态。

**Acceptance Scenarios**:

1. **Given** README 声明了 `template/` 的文件数，**When** 与仓库实际文件数比对，**Then** 两者相等。
2. **Given** README 列出了 `specs/` 下的目录，**When** 与实际存在的规格目录比对，**Then** 列表完整，没有遗漏任何一个。
3. **Given** README 声明了结构校验的项数，**When** 与校验工具实际的检查项数比对，**Then** 两者相等。

---

### User Story 4 — 工作区的合规由校验自动判定 (Priority: P3)

维护者改完工作区文档后运行日常校验，不需要人工记得去核对语言与事实。

**Why this priority**: 没有这一条，前三项在下一次迭代就会重新腐化——这正是本功能存在的原因。

**Independent Test**: 人为制造每一类违规，确认日常校验直接失败并指名问题所在。

**Acceptance Scenarios**:

1. **Given** 有人在工作区首页英文版写入一句中文散文，**When** 运行日常校验，**Then** 校验失败并指出文件与问题。
2. **Given** 有人改动了 `template/` 的文件数量而没有更新 README 中的数字，**When** 运行日常校验，**Then** 校验失败并同时给出声明值与实际值。
3. **Given** 新增了一个规格目录而 README 的目录表没跟上，**When** 运行日常校验，**Then** 校验失败并指出缺少哪一个。

### Edge Cases

- 工作区首页的中文译本与英文原文脱节时，如何与模板译本采用同一套新鲜度判定？
- 发布流程文档中的命令若随工具演进而改变，如何避免文档与实际再次脱节？
- 工作区首页提及的数字若来自多处（文件数、校验项数、规格目录数），是否都由同一机制核对？
- 模板仓库尚无任何标签或历史时，发布流程的「保护既有历史」步骤应当如何表现？

## Requirements *(mandatory)*

### 发布流程的正确性

- **FR-001**: 工作区中描述发布流程的文档必须给出一条在**模板仓库已有历史和标签**的情况下也能安全执行的步骤，执行后原有提交与标签必须仍可从默认分支到达。
- **FR-002**: 发布流程文档必须明确区分**首次发布到空仓库**与**后续发布到已有内容的仓库**两种情形，并说明各自适用的步骤；不得把只适用于其中一种的步骤呈现为通用步骤。
- **FR-003**: 发布流程文档必须写明此前那条步骤为什么不可再按原样用于后续发布，使读者不会从历史记录或旧仓库中把它捡回来。
- **FR-004**: 工作区中描述发布流程的两处——仓库首页与 `specs/001-chefs-pick-starter/quickstart.md` §B——必须彼此一致，不得一处已改、另一处仍写旧步骤。两处的现状不同，修法也不同：quickstart §B 讲的是**首次发布到新建的空仓库**，那个语境下现有步骤本身没错，缺的是它从未覆盖后续发布；首页则把这条只适用于空仓库的步骤当成了通用发布命令，是直接的错误。（`specs/002-english-first-docs/research.md` 中提及 `subtree split` 只是在解释为何摘要不能用提交哈希，不是可执行步骤，不在此列。）

### 工作区门面的语言

- **FR-005**: 工作区面向读者的首页必须以**英文为规范版本**，英文版散文中不得出现中文，且必须完整自足。
- **FR-006**: 中文以**独立译本文件**提供，译本散文中不得出现英文句子，必须覆盖英文原文的全部章节，并在顶部声明以英文版为准。
- **FR-007**: 禁止在工作区首页的任一语言版本内逐行或逐段并排两种语言，标题、表头、列表项、单元格同样适用。
- **FR-008**: 工作区首页的语言入口写法必须与模板引导层采用的写法一致，并双向可达。
- **FR-009**: 代码、命令、文件名、标识符、路径、产品名与语言入口中的语言名称不受单语要求约束。
- **FR-010**: 开发过程文件（规格、计划、任务、调研、契约、宪章）**不在本功能范围内**，继续使用中文。本功能只约束工作区面向读者的门面文档。

### 事实准确性

- **FR-011**: 工作区首页中声明的、可从仓库直接测得的事实——至少包括 `template/` 的文件数、`specs/` 下的规格目录清单、结构校验的检查项数——必须与仓库实际状态一致。
- **FR-012**: 上述每一项事实都必须由自动校验核对，不一致时**直接失败**，并同时报出声明值与实际值，使修正不需要人工查找。

### 自我约束的机制

- **FR-013**: 语言纯度、语言入口互指、中英章节一致、译本新鲜度这些已对 `template/` 生效的判定，必须同样覆盖工作区的门面文档。
- **FR-014**: 工作区门面文档的译本新鲜度必须与模板译本采用同一套判定方式，不得另造一套。
- **FR-015**: 本功能新增的校验必须并入现有的日常校验与发布门禁，不得要求维护者记住一条额外命令。
- **FR-016**: 新增校验不得改变任何既有检查项对 `template/` 的判定结果。

### 范围边界

- **FR-017**: 本功能不改变 `template/` 下的任何内容，也不改变模板交付给使用者的行为。
- **FR-018**: 本功能不向模板仓库推送任何内容；它只整理工作区自身。

## Success Criteria *(mandatory)*

- **SC-001**: 按工作区文档执行一次发布后，模板仓库中改造前已存在的提交与标签，仍可从默认分支到达的比例为 100%。
- **SC-002**: 工作区首页英文版中，剥离代码、命令、路径与语言入口后的中文字符数为 0（当前为 288）。
- **SC-003**: 英文读者读完工作区首页所需跳过的不可读内容占比从目前的约一半降为 0，且英文版承载的信息不少于现有双语版两侧合并后的内容。
- **SC-004**: 中文读者读完中文版首页所需跳过的不可读内容占比同样为 0。
- **SC-005**: 从工作区首页的任一语言版本到达另一语言版本，点击次数不超过 1 次。
- **SC-006**: 工作区首页中文版对其英文原文的章节覆盖率为 100%。
- **SC-007**: 工作区首页中可机读事实与仓库实际状态的偏差数为 0（当前已知偏差 2 处：文件数 26 对 28、规格目录清单缺 002）。
- **SC-008**: 语言纯度、语言入口互指、章节一致、事实准确性这四类判定，100% 由日常自动校验覆盖并在不满足时直接失败，不依赖人工检查。
- **SC-009**: 工作区中描述发布流程的 2 处，覆盖「首次发布」与「后续发布」两种情形且步骤可安全执行的比例为 100%（当前：首页 1 处把空仓库步骤当作通用步骤，属错误；quickstart §B 1 处在首次发布语境下正确，但两处都未覆盖后续发布）。
- **SC-010**: 改造后 `template/` 下文件的内容与本功能开始前逐字节相同，差异数为 0。
- **SC-011**: 既有 24 项结构校验对 `template/` 的判定结果在改造前后完全一致。

## Assumptions

- 工作区仓库是公开的，其首页会被外部访客看到，因此承担与模板首页同等的第一印象职责。这是把 002 的立论应用到工作区的前提。
- 「工作区面向读者的门面文档」目前仅有仓库根目录的 `README.md` 一份；`specs/`、`tools/`、`.specify/`、`.claude/` 下的内容均属开发过程文件或代码，不在此列。
- 宪章现行「附加约束 · 文档语言」条款的适用对象写的是「面向使用者的模板说明文档」，并明确把开发过程文件排除在外；工作区首页两头不靠。本功能按用户意图把该原则扩展到工作区门面，**这需要一次宪章修订**，属本功能的前置依赖，由 `/speckit-constitution` 单独完成，不在本规格的执行范围内。
- 模板仓库的发布采用单向同步；工作区不接受来自模板仓库的反向合并。
- 译本新鲜度沿用 002 已确立的内容摘要机制，理由同 002 调研 R3：提交哈希在两个仓库之间不通用。

## Dependencies

- **宪章修订**：需先把「文档语言」条款的适用范围扩展到工作区面向读者的门面文档，否则 FR-005 ~ FR-008 缺少上位依据。
- 功能 002 建立的语言结构契约与校验机制是本功能的复用基础；本功能扩展其适用范围，不重新设计。

## Out of Scope

- 把规格、计划、调研、契约、宪章等开发过程文件译成英文或改为英文规范版。
- 改动 `template/` 的任何内容，或改变模板交付给使用者的行为。
- 向模板仓库推送内容、创建标签或发布。
- 为工作区仓库补充 `CONTRIBUTING.md`、`CODE_OF_CONDUCT.md` 等协作文件——工作区不是面向社区贡献的项目，模板的社区标准要求针对的是由模板生成的仓库。
