# Chef's Pick OSS Starter Constitution

Chef's Pick OSS Starter（主厨精选开源仓库起步模板）是一个以 GitHub 模板仓库形式提供的轻量仓库脚手架，帮助个人项目和团队项目快速起步。它把开源社区各模块公认的佼佼者预先挑好、拼好，使用者不必自己搜集和拼接，只需专注于自己的想法和创作。每个版本具体覆盖哪些场景，由各功能规格界定。

## Core Principles

### I. 社区依据优先（Community-Proven Picks）

- 每个模块的选定来源必须有可核查的社区依据：Star 数、被成功开源项目实际采用的程度，或已成为事实标准（包括平台官方功能）。
- 只看 Star 数不够。Star 数高但没有权威背书、或与官方指引冲突的候选必须排除，例如 Go 团队明确表示不是官方标准的 golang-standards/project-layout。
- 作者个人偏好不得作为首要依据，只能在原则 II 的第 3 级使用，并且必须注明。
- 被刻意排除的知名候选必须记录排除理由。

**理由**：本项目的价值在于"选择来自社区，而不是作者的一厢情愿"。依据可核查，使用者才会信任这些选择。

### II. 认可度优先，其次易于起步（Selection Priority）

- 选型必须按以下顺序取舍：
  1. 社区认可度更高的方案优先。
  2. 认可度相当时，选择对仓库持有者更容易起步的方案，例如步骤更少、无需额外依赖或由平台内置。
  3. 仍然同样合格时，可以按作者个人偏好选择。
- 每个选型决定必须写明适用的是哪一级，并列出考虑过的备选方案。
- 判定"认可度相当"时必须写明依据，例如两者同为平台官方功能，或认可度数据处于同一数量级。

**理由**：固定的取舍顺序让每个选择都可预测、可复核，也把作者偏好限制在合理的位置。

### III. 来源与认可度透明（Transparent Provenance）

- 每个模块必须公开：选定来源及链接、上游许可证、认可度证据、核实日期和入选理由。
- 认可度证据必须如实标注类型：精确 Star 数、四舍五入的 Star 数、估算使用人数（须写明估算依据）、平台官方功能、事实标准（附具体采用者）或"未取得"。不得编造数字。
- 认可度数据至少每 6 个月复核一次，每次发布前也必须复核。
- 出现以下任一情况时，必须重新评估该模块：
  1. 上游末次提交超过 12 个月。以默认分支最近一次提交为准；仓库已归档视同满足本条件。
  2. 依赖已被广泛弃用的工具。
  3. 出现认可度明显更高的候选。

**理由**：Star 数和维护状态会变化。只有带日期、可追溯的数据，才能长期支撑使用者的信任。

### IV. 开箱即用（Ready Out of the Box）

- 从模板生成仓库必须一步完成，不需要安装额外工具或运行生成器；生成后即具备完整仓库的核心要素。
- 交付的文件必须是已填好、可直接使用的内容。只有项目身份信息（项目名、所有者、联系方式等）使用占位符；占位符格式统一，一次搜索即可全部找到，并由起步清单逐项引导替换。
- 模板作者的身份信息（署名、联系方式、赞助链接）不得作为生成项目自身的信息出现，例如不得出现在项目的许可证版权人、赞助入口或联系方式中。模板自身的版本历史也不得作为生成项目的变更记录出现。
- 模板自身的介绍、讲解、选型清单、维护说明、许可证声明和变更记录，只能放在明确标注的起步引导层中，并且必须能一步移除。GitHub 从模板建仓库时会原样复制默认分支，所以这一层无法避免被复制。
- 模板的开发过程文件（功能规格、实施规划、Spec Kit 和 AI 助手的配置等）不得进入生成的仓库。
- 生成仓库的自动检查在还没有代码时也必须能通过。

**理由**：使用者应当专注于自己的想法和创作，而不是清理和拼装仓库琐事。

### V. 轻量而完整（Lightweight but Complete）

- "麻雀虽小，五脏俱全"：核心要素必须齐全，至少包括项目说明、许可证、忽略规则、协作规范（行为准则、贡献指南、安全策略）、Issue 与合并请求模板、变更记录，以及基础的自动检查和依赖更新。
- 不得把重型脚手架、脚手架生成器或基金会级成套模板作为默认方案。本项目只提供与编程语言无关的内容。
- 非核心的附加内容必须是可选的：默认不产生可见副作用，可以单独删除且不影响其余部分。难以做到简洁可靠的附加内容，宁可不做。

**理由**：个人项目需要完整但不臃肿的起点。每多一项默认内容，都会增加使用者的清理负担和项目的维护负担。

## 附加约束（Additional Constraints）

- **平台**：本项目面向 GitHub，依赖其模板仓库、社区健康文件、Issue 表单、自动生成发布说明、Dependabot、Actions、私有漏洞报告等原生能力。其他代码托管平台不在范围内。
- **文档语言**：面向使用者的模板说明文档（首页介绍、选型清单、起步清单、讲解、维护说明、模板变更记录）以**英文为规范版本**。英文版必须完整自足，散文中不得夹杂中文；中文以**独立的译本文件**提供，译本散文中不得夹杂英文，必须覆盖英文版的全部章节，并在顶部声明以英文版为准。禁止在同一文档内逐行或逐段并排两种语言，标题、表头、列表项、单元格同样适用。每份文档顶部必须有写法统一的语言入口，使任一语言版本都能一步到达同一文档的其他语言版本；某语言版本尚不存在时，入口不得列出该语言，也不得产生失效链接。译本必须与其英文原文同处起步引导层，以保证原则 IV 的一步移除仍然成立；由工具批量刷新的机器可读数据只保留一份，其他语言版本引用而不复制。代码、命令、文件名、标识符、产品名、许可证标识，以及语言入口中的语言名称，不受上述单语要求约束。生成仓库中的协作文件及其中的来源注释必须使用英文，本条不向生成的仓库新增任何中文文件。开发过程文件（规格、规划、宪章等）不受此限，目前使用中文。

  **依据**：对 25 个仓库的一手抽样显示，根 README 的规范版本一律为英文（正文中文字符占比 0.0%–0.6%），逐段并排的写法在 20 个受检仓库中出现 0 次；本项目选定的来源 Contributor Covenant、GitHub Open Source Guides、Keep a Changelog、SemVer 也全部采用「英文规范版本 + 独立译本 + 语言入口」。取证记录见 `specs/002-english-first-docs/spec.md`。按原则 I，社区共识优先于作者对排版的个人偏好。
- **许可证与署名**：模板仓库以 MIT 许可证发布，并声明从本模板生成的项目无需保留模板作者的署名。收录或改写的上游内容必须逐一核对许可证，并按要求保留署名，但不得因此给使用者增加额外的合规负担。
- **自动化安全基线**：生成仓库引用的每个 GitHub 动作都必须固定到完整的提交哈希，并在同一行注明版本号，由依赖自动更新定期升级。工作流令牌默认只读，只有确实需要的步骤才单独提升权限。

## 开发流程与质量门禁（Development Workflow & Quality Gates）

- **规格驱动**：新功能按 Spec Kit 流程推进（specify → clarify → plan → tasks → implement）。规划阶段必须先通过宪章检查（Constitution Check），才能进入设计。
- **选型变更**：新增、替换或移除模块时，必须在同一次变更中同步更新选型清单（来源、认可度、核实日期、理由、备选方案）和模板自身的变更记录，并写明原因。
- **自用一致性**：模板仓库自身必须遵循它交付给使用者的规范，包括社区标准自检页全部达标，变更记录采用 Keep a Changelog 格式和语义化版本。
- **发布门禁**：每次发布前必须逐项确认：
  1. 所有认可度数据的核实日期不早于发布前 30 天。
  2. 从模板新生成的仓库核心要素齐全，首次自动检查通过。
  3. 占位符能一次搜索全部找到；起步引导层之外没有模板作者身份信息、模板版本历史或开发过程文件；执行清理命令后，起步引导层被完整移除，且没有留下失效的引用。
  4. 按起步清单完成定制后，社区标准自检页全部达标。
  5. 所有动作引用都已固定到提交哈希，工作流令牌默认只读。
  6. 全部译本与当前英文原文对齐：章节集合一致，语言入口双向可达，没有指向不存在译本的链接，且译本顶部的规范性声明仍然指向对应的英文原文。
- **体验指标**：首次起步用时这类体验指标只作观察，不作为发布门槛。作者在发布后自行使用模板，记录发现的问题，并在后续版本中改进。

## Governance

- 本宪章高于项目中的其他实践约定。功能规格、实施规划、任务和实现都必须遵守本宪章；发生冲突时，要么修改方案，要么先修订宪章。
- **修订流程**：修订必须以书面形式提出，写明动机和影响，经项目维护者批准后生效。每次修订都要更新版本号和"最近修订"日期，在文件顶部的同步影响报告中记录变更，并检查依赖宪章的模板和命令是否需要同步调整。同步影响报告是本宪章的组成部分，必须随修订一并提交并长期保留在文件顶部，不得在提交前删除；历次报告按从新到旧的顺序累积，使每一次修订的动机和影响都可追溯。
- **版本策略**：采用语义化版本。
  - MAJOR：删除或重新定义原则。
  - MINOR：新增原则或章节，或实质性扩充指引。
  - PATCH：措辞澄清或非语义性修改。
- **合规复核**：每次 `/speckit-plan` 的宪章检查必须逐条对照原则 I–V 和附加约束。确有必要违反时，必须在规划的复杂度跟踪（Complexity Tracking）中说明理由，以及为什么放弃更简单的方案。每次发布前，按"开发流程与质量门禁"逐项核对。
